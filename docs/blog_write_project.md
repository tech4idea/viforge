# blog-write 产品讨论稿

## 背景

计划在 ViForge 中增加博客写作和发表类项目。

- 项目 ID：`blog-write`
- 项目描述：日常博客、公众号写作
- 初始平台：微信公众号、知乎
- 核心目标：把日常深入思考沉淀成博客、公众号或知乎文章，并辅助生成平台草稿

典型场景：

用户日常遇到一些深入思考，希望把它写成博客、公众号或知乎文章进行发布分享。前期的写作思路讨论、信息收集、头脑风暴、框架构建、标题拟定、正文书写、配图生成、润色修改等都在本地工作目录完成。形成正式稿后，再通过浏览器操控、图片上传等工具，由 Agent 协助在对应平台生成草稿。用户确认后自行决定是否发布。

## 产品形态判断

`blog-write` 应作为 ViForge 的新增 product profile，而不是新建一套独立应用。

原因：

- 当前仓库已有 `novel-adaptation`、`sitcom`、`study` 等 product profile，底层工作区、会话、LangGraph agent、skills、图片生成、Playwriter 浏览器操控、项目记忆和模板能力可以复用。
- 博客写作的差异主要在产品 profile、默认模板、写作提示词、平台发布 SOP 和草稿检查标准。
- 第一阶段重点不是做复杂工作流，而是让用户围绕一篇文章高效完成讨论、写作、修改和平台草稿生成。

初步结论：

- 新增产品 ID：`blog-write`
- 产品名称可暂定为：`博客写作工作台`
- 第一阶段目标：完成本地写作协作，不承诺自动发布正式文章
- 发布权限边界：Agent 可以协助创建或更新平台草稿；最终发布必须由用户亲自确认或执行

## 工作区结构调整

博客写作不适合按“灵感、资料、大纲、草稿、配图、发布、复盘”拆成固定流程目录。实际写作通常围绕一篇文稿持续迭代，流程拆分过细会增加维护成本，也会打断写作。

第一版项目模板应以“单篇文稿”为中心，主题空间由用户按需要手动创建文件夹。

建议默认结构：

```text
正文.md
素材/
配图/
发布/
发布/微信公众号发布SOP.md
发布/知乎发布SOP.md
发布/发布记录.md
发布/发布检查清单.md
```

说明：

- `正文.md` 是主要工作文件，承载标题、大纲、草稿、最终稿和修改记录。Agent 默认围绕这个文件工作。
- `素材/` 用于保存参考资料、摘录、链接、截图、事实核查记录等。是否细分由用户决定。
- `配图/` 用于保存生成图、封面图、截图和图片提示词。
- `发布/` 用于沉淀平台发布 SOP、踩坑记录、草稿生成记录和发布前检查结果。
- 暂不把平台 SOP 放入隐藏知识库目录。先放在项目目录下，方便用户直接查看、修改和积累。等流程稳定后，再考虑迁移到全局知识库或模板库。

如果用户需要按主题管理多篇文章，可以手动创建：

```text
AI 产品思考/
技术实践/
读书笔记/
行业观察/
```

每个主题文件夹内部可以继续使用同样的轻量结构，或者只放单个 Markdown 文稿。

## Agent 分工调整

第一阶段不需要把大纲、正文、润色、配图拆成多个专业 agent。博客写作更适合一个主写作 agent 贯穿完整过程，减少上下文切换。

建议默认 agent/skill：

- `blog-writing-agent`：负责选题讨论、标题备选、大纲、正文写作、改写、扩写、压缩、润色、风格统一、配图建议和图片提示词。
- `research-agent`：按需负责资料收集、事实核查、引用出处整理和争议点标注。
- `publisher-agent`：按平台 SOP 操控浏览器创建或更新草稿，不负责最终发布。
- `reviewer-agent`：基于平台预览、截图、DOM 或导出的草稿内容检查文章内容、排版、图片和平台适配问题。

边界：

- `blog-writing-agent` 默认只改本地工作区文稿和素材，不直接操作发布平台。
- `publisher-agent` 只生成草稿，不点击正式发布。
- `reviewer-agent` 必须检查平台实际渲染效果，不能只读本地 Markdown 后假设平台效果正确。

## 平台发布流程

发布能力拆成三层：平台 SOP、浏览器工具执行、草稿检查。

### 平台 SOP

第一版在项目目录中维护平台 SOP：

```text
发布/微信公众号发布SOP.md
发布/知乎发布SOP.md
发布/微信公众号踩坑记录.md
发布/知乎踩坑记录.md
```

SOP 内容建议包括：

- 登录与账号状态检查
- 新建草稿入口
- 标题、正文、封面、摘要、话题等字段位置
- Markdown 到平台富文本的粘贴策略
- 图片上传流程
- 常见失败现象和恢复方式
- 发布前检查项
- 禁止 Agent 自动执行的动作

这样浏览器自动化的不稳定性可以通过持续修订 SOP 来降低，而不是过早把流程硬编码进工具。

### 浏览器工具执行

当前 LangGraph runtime 已有 Playwriter Browser Tools，适合连接用户已登录的真实浏览器标签页。

初步策略：

- 用户先在浏览器登录微信公众号或知乎，并授权 Playwriter 标签页。
- Agent 调用浏览器快照能力确认当前页面和可操作控件。
- Agent 按项目目录中的平台 SOP 填写草稿。
- 每个关键阶段写入 `发布/发布记录.md`，记录成功步骤、失败步骤、页面状态和恢复动作。

对于微信公众号编辑器这类富文本场景，优先探索两种策略：

- 粘贴 HTML：本地把最终稿转换成受控 HTML，再复制或注入到编辑器。
- 分块填充：标题、摘要、正文、图片逐块处理，并在每一步后读取页面状态。

具体哪种更稳定，需要通过真实平台试跑后决定。

### 草稿检查

为了让 Agent 真正“看懂”平台上的成稿效果，检查不能只停留在本地 Markdown。

建议检查：

- 读取平台编辑器 DOM，确认标题、段落、列表、图片数量和顺序。
- 截图后做视觉检查，识别明显排版问题。
- 优先检查平台预览页，而不是只检查编辑页。
- 把检查结论写入 `发布/发布检查清单.md`。

后续可以把常见问题沉淀成规则，例如：

- 标题不能为空。
- 图片不能丢失。
- 一级标题数量合理。
- 正文首屏不应只有图片。
- 段落不应整篇居中。
- 连续空行不能过多。
- 字号、标题居中、图标使用不能明显异常。

## 美观性的可衡量标准

“美观”需要拆成可执行检查项，否则 Agent 很难稳定优化。

内容层：

- 标题是否准确、有吸引力且不标题党。
- 开头是否在 3 段内说明问题或给出钩子。
- 每个小节是否服务于核心观点。
- 是否存在未经核实的事实、数据或引用。
- 结尾是否有明确收束或行动建议。

结构层：

- 小标题层级是否清楚。
- 段落长度是否适合移动端阅读。
- 列表、引用、加粗是否使用克制。
- 是否存在过长段落、重复观点或跳跃论证。

视觉层：

- 标题、正文、小标题、引用样式是否一致。
- 图片是否清晰、比例合适、与上下文相关。
- 图片前后是否有必要解释。
- 是否出现整篇居中、字号异常、图标误用、空白过多等问题。
- 微信或知乎预览页是否在手机宽度下可读。

平台层：

- 微信公众号：封面、摘要、合集、话题、原创声明等字段是否符合预期。
- 知乎：标题、正文、话题、图片、引用和外链展示是否符合预期。
- 草稿是否保存成功，是否能重新打开继续编辑。

这些检查项可以作为 `reviewer-agent` 的默认指令，也可以作为 `发布/发布检查清单.md` 的模板。

## 分阶段实现建议

### 第一阶段：本地写作 profile

目标：让 `blog-write` 作为产品可创建项目，并支持围绕 `正文.md` 的本地写作协作。

需要做：

- 在 `packages/shared/src/productProfiles.ts` 增加 `blog-write` profile id。
- 增加轻量默认目录和文件：`正文.md`、`素材/`、`配图/`、`发布/`。
- 增加 `packages/shared/src/product-profiles/blog-write/profile.json`。
- 增加默认 prompts：`blog-writing-agent`、`research-agent`、`publisher-agent`、`reviewer-agent`。
- 更新共享合同、默认产品选择和文档。
- 跑 API/web typecheck。

这一阶段不承诺自动打开平台，只完成本地写作工作台。

### 第二阶段：平台草稿生成 MVP

目标：选择一个平台先跑通草稿生成。平台顺序待定，知乎可能编辑器更轻，微信公众号更贴近核心需求。

需要做：

- 在项目目录维护对应平台 SOP。
- 准备一篇测试文章，从 `正文.md` 生成平台草稿。
- 记录 Playwriter 操作流程、失败点和恢复动作。
- 让 `publisher-agent` 把结果写入 `发布/发布记录.md`。
- 用户确认前不发布。

### 第三阶段：微信公众号草稿生成

目标：支持公众号草稿生成和预览检查。

需要做：

- 完善 `发布/微信公众号发布SOP.md`。
- 明确正文粘贴策略、图片上传策略、封面图策略。
- 增加平台预览检查清单。
- 沉淀踩坑记录，作为 publisher/reviewer 的上下文。

### 第四阶段：质量评估和回归

目标：把踩过的坑变成可复用测试、SOP 和 agent 指令。

需要做：

- 每次发布失败后记录失败页面、原因、修复方式。
- 抽取典型案例进入 harness/eval fixture。
- `reviewer-agent` 输出结构化结果：`passed`、`issues`、`requiredFixes`、`platformRisks`。
- 对平台 SOP 做版本化维护。
- 流程稳定后，再考虑把通用平台 SOP 从项目目录迁移到全局知识库或模板库。

## 待确认问题

1. 产品名称是否使用 `博客写作工作台`，还是需要更偏公众号或自媒体的名称？
2. 第一批平台优先级是知乎优先，还是微信公众号优先？
3. 文章类型是否主要是个人思考、经验总结、技术文章，还是也包括商业宣传、产品更新、课程文章？
4. 配图以 AI 生成封面和插图为主，还是更多使用用户已有截图和素材？

## 当前收敛结论

- `blog-write` 做成 ViForge 的第四个 product profile。
- 默认项目模板改为单篇文稿中心，不按写作流程拆目录。
- 大纲、正文、润色、配图先合并到一个 `blog-writing-agent`。
- 平台 SOP 第一阶段放在项目目录 `发布/` 下维护，后续稳定后再考虑迁移到知识库。
- 发布自动化只负责生成草稿，不自动点击正式发布。
- 草稿质量检查必须基于平台实际预览、截图或 DOM，而不是只看本地 Markdown。
