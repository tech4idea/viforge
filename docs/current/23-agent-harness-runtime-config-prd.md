# Agent Harness RuntimeConfig PRD

## 1. 背景

当前 Agent Harness 已具备候选配置、评测案例、EvalRun、人工审阅和发布审计等能力，但用户在使用时需要理解过多内部概念，例如 AgentSpec、LayerConfig、PromptBlock、ToolDescription 等。这些概念之间存在组合和包含关系，导致用户难以判断一次修改的真实生效范围，也难以理解评测和发布到底针对什么对象。

新一版 Harness 需要把对外产品概念收敛为“运行配置流程”。用户围绕一次配置流程完成查看、编辑、评测、发布和回滚；流程中拆分为评测案例上下文、Agent 配置、评测运行配置、断言配置和人工审阅模板等节点。行为规则、工具说明和 Agent 提示词作为 Agent 配置呈现；断言和人工审阅模板只用于评测验证，不混入评测案例，也不混入 Agent 配置。

本系统面向单机桌面版自用场景，不设计多用户、多角色、审批流或权限分工。所有配置、评测、审阅、发布和回滚动作都由本机用户本人完成；审计记录用于用户自己复盘、比较和回滚。

## 2. 产品目标

1. 降低理解成本：用户只需要理解“运行配置”是发布和生效单位。
2. 明确生效范围：每次配置改动都能清楚标明作用于 system、product 还是 agent。
3. 支持可验证发布：任何候选运行配置在发布前都可以通过固定案例评测和人工审阅验证。
4. 保留审计能力：每次发布、强制发布和回滚都能追踪改动内容、评测结果和人工决策。
5. 支持节点配置复用：评测案例上下文、Agent 配置、评测运行配置、断言配置和人工审阅模板都可以从历史流程中复用或派生。
6. 支持本机自用审计：发布、强制发布和回滚都保留本地记录，但不引入多人审核和权限审批。

## 3. 非目标

1. 不做项目级 Harness 配置覆盖。项目个性化通过项目文件、项目 memory、工作区模板和用户 prompt 表达。
2. 不把 Harness 做成项目内容编辑器。
3. 不用程序断言替代人工质量判断。
4. 不在未发布状态影响普通运行。
5. 不要求用户理解内部数据表或代码对象名称。
6. 不做多用户角色、审批流、管理员权限或协作分工。
7. 暂不做产物结构配置发布。产物结构牵涉历史上下文和记忆重建，当前只允许在断言中引用现有结构要求，不允许通过 Harness 修改并发布新的产物结构约束。

## 4. 用户场景

### 单机自用用户

用户在自己的单机桌面版 ViForge 中调整 Agent 配置、构造评测上下文、配置评测运行策略和断言、填写人工审阅并决定是否发布。系统不区分配置维护者、评测维护者或发布审核者，也不出现“提交给别人审核”的流程。

用户需要完成的任务包括：

- 查看历史配置流程，按状态、产品、agent、标签、更新时间和发布状态筛选排序。
- 基于历史流程复用某个节点配置，或新建一个节点配置表单。
- 从历史对话或失败运行反查对话起点，构建评测案例上下文。
- 编辑 Agent 提示词、工具说明和行为规则。
- 配置评测运行策略、断言配置和人工审阅模板。
- 查看评测结果，自己打分审阅，自己决定发布、强制发布、回滚或归档。

所有动作都只对本机用户自己负责。

## 5. 核心概念

### 运行配置

运行配置是 Agent Harness 的核心对象。它代表某个产品当前或候选的完整 agent runtime 配置。

运行配置包含：

- Agent 提示词。
- 行为规则。
- 工具说明。
- 记忆、检索、模型、工具权限等运行策略。
- 生效范围和改动说明。

运行配置有状态：草稿、候选、已发布、已归档。

### 生效范围

所有配置片段都必须标明生效范围。

| 范围 | 含义 |
| --- | --- |
| system | 跨产品共享的系统级配置。 |
| product | 某个产品下所有项目默认生效的配置。 |
| agent | 某个产品下指定 agent 生效的配置。 |

不支持 project 级 Harness 配置。

### 配置片段

配置片段分为两类：一类是发布后普通 run 会读取的 Agent runtime 配置片段，另一类是只用于评测验证的配置节点。二者都可以命名和复用，但只有 Agent runtime 配置片段属于候选运行配置的发布内容。

| 片段 | 含义 |
| --- | --- |
| Agent 提示词 | 某个 agent 的职责、流程和边界。 |
| 行为规则 | agent 工作时要遵守的规则，例如质量门槛、输出格式、写文件边界。 |
| 工具说明 | 模型看到的工具描述、参数说明和输出说明。 |
| 运行策略 | 普通 run 会读取的模型、记忆、检索、工具权限等策略。 |
| 评测运行配置 | EvalRun 怎么跑，例如 Repro/Live、模型临时覆盖、固定 memory/knowledge 读取和高风险工具 mock。 |
| 断言配置 | 只在评测时使用的程序断言集合，例如文件变化、路径约束、工具调用和 diff 限制。 |
| 人工审阅模板 | 只在人工审阅 EvalRun 时使用的打分项、权重、决策选项和备注提示。 |

产物结构暂不作为可编辑配置片段。当前可以在断言配置中引用既有正式结构要求，但不允许在 Harness 中修改并发布产物结构。

断言配置、人工审阅模板和评测运行配置不是 Agent 配置，也不是普通 run 的生效配置。它们保存后只进入评测验证链路，用来生成 EvalRun、程序断言结果和人工审阅表单。

### 评测案例

评测案例只负责构建一次对话开始前的上下文环境。它不是断言集合，也不包含人工评分标准。这样可以避免“案例断言”和“运行断言”两个概念重复。

评测案例包含：

- 对话起点用户输入或历史对话消息。
- 对话开始前的最近上下文。
- 工作区快照。
- 固定的记忆和知识库输入。
- 可选标签和说明。

第一版主路径从历史对话消息或失败运行反查对话起点生成评测案例。手动创建作为后续能力预留：用户可以手写起点消息并选择或上传上下文，但新建动作只生成表单，必须通过完整性和敏感信息裁剪校验后才能保存。

### 断言配置

断言配置是评测运行时使用的程序检查规则集合，可以独立命名、复用和派生。

断言配置包含：

- 文件变化断言。
- 路径和目录约束。
- Markdown section 或文本结构断言。
- 工具调用顺序和参数断言。
- diff 数量、allowed paths、allowed changes 等限制。

断言配置不属于评测案例。用户可以在步骤三选择历史断言配置，或选择“新建断言配置...”打开未保存表单；只有填写有效断言并通过合法性校验后，点击保存或下一步才创建配置。

### 人工审阅模板

人工审阅模板定义人工审阅 EvalRun 时使用的打分项和决策选项，可以独立命名、复用和派生。

人工审阅模板包含：

- 模板名称。
- 打分项和权重；每个打分项的运行评分范围固定为 1-10 分。
- 总备注、文件备注和行级备注提示。

新建审阅模板只打开配置表单，不立即保存。必须至少配置一个打分项、总权重合法、决策选项完整后，点击保存或下一步才创建模板。模板中的打分项可以新增、删除和调整权重；这些改动保存后形成新的模板版本，不回写原始模板版本。

### 节点配置复用与新建

评测案例上下文、Agent 配置、评测运行配置、断言配置和人工审阅模板都支持复用。

每个节点使用一个选择框完成“选择历史配置”与“新建配置”两种动作：

- 选择历史配置：直接加载该配置作为当前节点输入。
- 选择“新建...”：只生成一个未保存的配置表单，不提示创建成功，不写入候选。

新建配置必须满足：

- 支持用户自定义名称；未命名时使用人类可读的自动命名，例如“产品 / agent / 配置类型 / 时间”。
- 用户必须完成实际修改。
- 系统必须校验内容完整性、合法性和是否有真实差异。
- 只有点击保存或下一步并通过校验后，配置才真正创建或更新。

复用后的修改不会回写原始配置版本。选择历史配置只是把该版本作为当前节点的起点，后续编辑和保存会生成新的候选版本或新版本引用；原始版本保持不变，仍可继续被其它流程复用。

### 评测运行

评测运行是候选运行配置在某个评测案例上的一次执行结果。

评测运行包含：

- 输出结果。
- 文件变化。
- 工具调用记录。
- 程序断言结果。
- 人工审阅结果。

### 发布记录

发布记录记录一次运行配置发布、强制发布或回滚行为。

发布记录包含：

- 发布对象。
- 改动摘要。
- 影响范围。
- 评测结果。
- 人工审阅结论。
- 本机用户备注。
- 是否强制发布及原因。

## 6. 功能范围

### 6.1 运行配置总览

用户可以从 Harness 入口查看所有历史配置流程，并进入当前产品的已发布运行配置。

入口页是独立的历史流程列表，不做弹窗，也不在同页展开流程详情。搜索、筛选、排序和列表占据页面主宽度；每一行提供操作字段。点击查看或修改后进入具体配置流程页，由配置路线图统一承载流程概览、改动清单、评测、审阅和发布记录。

入口列表需要支持：

- 搜索流程名、配置名、agent 和标签。
- 按状态、产品、agent、标签、更新时间和发布状态筛选。
- 按更新时间、创建时间、Gate 状态和评测完成度排序。
- 每个列表项提供操作字段，支持查看、修改、发布检查、回滚、归档或删除未引用草稿。

页面需要展示：

- 当前已发布版本。
- 最近候选版本。
- 配置片段组成。
- 每个片段的生效范围。
- 相比上一个发布版本的改动摘要。
- 当前配置适用的 agent 列表。

验收标准：

- 用户能在一个页面判断当前普通运行会使用哪套配置。
- 用户能看出某条规则或工具说明是 system、product 还是 agent 范围。
- 用户不需要理解 AgentSpec 或 LayerConfig 才能判断生效对象。
- 用户能通过筛选和排序快速找到历史配置流程。

### 6.2 创建候选运行配置

用户可以基于当前已发布配置创建候选运行配置。

候选可以来自以下改动：

- 修改某个 agent 的提示词。
- 新增、修改或移除行为规则。
- 修改工具说明。
- 修改模型、记忆、检索或工具权限策略。
- 选择或修改评测运行策略。

断言配置和人工审阅模板不属于候选运行配置的发布内容。它们属于评测验证节点：可以在同一流程里创建、复用和绑定到评测运行，但保存它们本身不代表修改普通 run 会读取的 Agent runtime 配置。

每次候选必须生成改动清单。

改动清单中的每一项必须包含：

- 生效范围。
- 改动类型。
- 改动对象。
- 改动摘要。

验收标准：

- 用户保存任意配置改动后，系统生成一个候选运行配置。
- 用户选择“新建配置”时不能立即生成候选；必须有实际修改并通过校验，点击保存或下一步后才生成或更新候选。
- 候选不会影响普通运行。
- 用户能看到候选相对当前已发布配置的差异。
- 用户能看到当前节点配置来自哪个历史流程或是否为新建派生版本。

### 6.3 配置片段管理

用户可以管理运行配置中的 Agent 配置片段，并在步骤三管理评测运行配置、断言配置和人工审阅模板。这里的“评测运行配置”只描述 EvalRun 怎么跑，例如 Repro/Live、模型临时覆盖、memory/knowledge 读取方式和高风险工具 mock；它不是发布后普通 run 读取的运行配置。

所有可复用节点配置都遵循同一交互规则：一个选择框同时列出历史配置和“新建...”入口；新建只打开表单，不保存；保存或下一步时统一校验。

#### Agent 提示词

用户可以查看和编辑每个 agent 的主体提示词。

要求：

- 明确显示 agent 名称和生效范围。
- 支持查看当前已发布版本和候选版本差异。
- 修改后生成候选运行配置。
- 如果同一 Agent 配置里同时修改多个 agent 提示词，页面应按 agent 列出多个原子变更项，但仍保存为同一个候选运行配置。
- Harness 只校验提示词配置结构是否完整、版本差异是否存在、引用关系是否合法，不做提示词语义内容审查。

#### 行为规则

用户可以查看、新增、编辑、停用行为规则。

要求：

- 行为规则必须标明生效范围。
- 行为规则必须有标题和正文。
- 修改后生成候选运行配置。
- 如果同一 Agent 配置里同时修改多个行为规则，页面应按规则逐条展示变更和差异，但仍合并为同一个候选运行配置。
- Harness 只校验行为规则结构是否完整、版本差异是否存在、引用关系是否合法，不做内容语义审查。

#### 工具说明

用户可以查看和编辑工具说明。

要求：

- 选择工具后显示当前正式说明。
- 支持编辑工具主描述、参数说明、输出说明。
- 明确显示该工具说明的生效范围。
- 修改后生成候选运行配置。
- 如果同一 Agent 配置里同时修改多个工具说明，页面应按 toolId 列出变更项，并在保存时一次性生成同一个候选运行配置。
- Harness 只校验工具说明结构是否完整、版本差异是否存在、引用关系是否合法，不做内容语义审查。

#### 多片段变更呈现

Agent 配置阶段允许同一候选里同时存在多个原子变更项，例如同时改 2 个 agent 提示词、3 条行为规则和 4 个工具说明。界面不把这些改动拆成多个候选，而是：

- 上层按“Agent 提示词 / 行为规则 / 工具说明”分区。
- 分区内按具体 agent、规则标题或 toolId 展示多条变更卡片。
- 每条变更卡片都显示来源版本、目标版本、差异摘要和生效范围。
- 保存时统一校验所有变更项的合法性、真实差异和范围约束，然后生成一个候选运行配置和一份改动清单。

#### 普通运行策略

用户可以查看和调整模型、记忆、检索、工具权限等策略。

要求：

- 策略必须标明生效范围。
- 策略改动必须进入候选运行配置的改动清单。
- 普通运行策略配置可以复用历史运行配置，也可以新建派生版本。

#### 评测运行配置

用户可以选择、复用、新建和编辑评测运行配置。

要求：

- 评测运行配置必须有名称。
- 必须明确 Repro 或 Live 模式。
- Repro 模式必须说明 memory/knowledge 从案例固定输入读取，写入默认为 mock 或隔离记录。
- Live 模式必须显式选择，并提示会读取当前 live memory/knowledge。
- 模型、工具权限和高风险工具 mock 属于评测执行策略，不会随候选运行配置发布到普通 run。

#### 断言配置

用户可以选择、复用、新建和编辑断言配置。

要求：

- 断言配置必须有名称。
- 断言配置可以新增。选择“新建断言配置...”只打开未保存表单，不立即创建记录。
- 至少包含一条有效断言。
- 路径、工具、diff 等条件必须可执行。
- 断言配置不放在评测案例中。
- 修改后只影响评测和发布 Gate，不影响普通运行。
- 断言配置界面必须独立于评测案例上下文展示。步骤三中既要能在评测运行配置里选择已保存断言配置，也要能展开断言配置表单进行新建或派生编辑。
- 断言配置按类型分组呈现：文件变化、路径约束、Markdown section、工具事件、diff 限制和现有结构合规。
- Harness 只校验断言结构合法性，例如断言类型、目标路径、工具 ID、比较条件、启停状态和引用关系，不判断断言是否“合理”或是否覆盖业务风险。

步骤三的页面主次关系应以断言配置为核心。评测运行配置只有有限的执行参数，例如 Repro/Live、模型临时覆盖、memory/knowledge 读取方式和工具 mock，适合做成紧凑区块；断言配置会持续增长，必须占据主要编辑面积，支持分组、批量新增、启停、复制、删除和逐条结构校验。

#### 人工审阅模板

用户可以选择、复用、新建和编辑人工审阅模板。

要求：

- 模板必须有名称。
- 至少包含一个打分项。
- 打分项权重必须合法。
- 决策选项必须完整。
- 模板用于渲染人工审阅表单，不影响普通运行。

#### 产物结构

当前版本不提供产物结构配置发布能力。

要求：

- 不允许在 Harness 中修改并发布产品产物结构。
- 断言配置可以引用现有结构要求做评测检查。
- 后续若开放产物结构配置，需要同时设计历史上下文和记忆重建策略。

### 6.4 评测案例库

用户可以选择、复用、新建和维护评测案例上下文。

案例来源：

- 历史对话消息。
- 失败运行记录。
- 失败运行反查到的历史对话起点。
- 手动创建表单，作为后续预留能力。

案例内容：

- 对话起点用户消息。
- 对话开始前的最近上下文。
- 工作区快照。
- 固定记忆。
- 固定知识库检索结果。
- 标签。

验收标准：

- 用户能从历史对话或失败运行快速生成评测案例上下文。
- 用户能复用历史评测案例上下文。
- 用户能区分评测输入和运行配置。
- 用户不会在评测案例步骤看到断言配置。

### 6.5 评测执行

用户可以选择候选运行配置、评测案例上下文、评测运行配置、断言配置和人工审阅模板执行评测。

这一步允许同一个 Agent 配置搭配不同评测运行配置、断言配置或人工审阅模板重复执行，用于比较不同验证策略下的结果。评测运行配置、断言配置和人工审阅模板都可以独立命名、复用和派生，但不会随候选运行配置发布到普通 run。

评测模式：

- Repro：使用固定记忆和固定知识库输入。
- Live：使用当前 live 记忆和知识库。

评测结果需要展示：

- 运行状态。
- 输出内容。
- 文件变化。
- 工具调用。
- 程序断言。
- 与当前已发布配置的对比。

评测报告和人工打分的页面关系：

- 二者是步骤四下的两个平级主工作区，不是主内容和右侧辅助栏的关系。
- 评测报告负责承载运行产物、断言结果、active/candidate 对比、文件 diff、工具调用和行级备注定位。
- 人工打分负责承载审阅模板选择、逐项评分、权重调整、决策和备注提交。
- 两个工作区都应占用主内容宽度；可以用上下分区、页内锚点或顶部切换组织，但不能把人工打分挤入窄侧栏。
- 当屏幕较宽时，也不应把人工打分降级为右侧信息栏；最多只允许在同等权重的双主面板中并排，并保证打分表有足够列宽。

验收标准：

- 候选运行配置可以在不污染真实项目的情况下被评测。
- 用户能判断候选是否通过程序断言。
- 用户能看到 active 和 candidate 的表现差异。
- 同一个 Agent 配置可以搭配不同评测运行配置、断言配置或审阅模板执行评测。

### 6.6 人工审阅

用户可以对评测运行进行人工审阅。

人工审阅前必须选择人工审阅模板。模板决定审阅表单的打分项、权重、决策选项和备注提示。

人工审阅区与评测报告区平级展示。用户查看评测报告后进入人工打分，但人工打分不是评测报告的侧边栏，也不是报告里的补充小组件。它是独立的主操作区，因为打分项可能很多，还需要新增、删除、调整权重、填写分值和备注。

审阅内容：

- 总分和分项评分。
- 文字备注。
- 文件或行级备注。

人工审阅必须提供逐项打分区：

- 系统按所选人工审阅模板渲染所有打分项。
- 每个打分项都必须被逐项检查，状态为“已评分”或“不涉及”。
- 涉及的打分项必须填写 1-10 分；不涉及的打分项可以跳过分值，但必须显式标记“不涉及”并可填写备注。
- 总分按涉及项的权重加权计算，不涉及项不参与总分。
- 用户可以在审阅前或审阅中派生新模板，新增、删除打分项或调整权重；派生模板保存后再用于当前审阅。

验收标准：

- 发布前可以看到人工审阅结论。
- 人工审阅可以补充程序断言无法判断的质量问题。
- 退化或失败案例可以反向沉淀为新评测案例。
- 用户可以复用历史审阅模板，也可以新建模板表单；新建模板必须通过打分项和权重校验后才保存。
- 未逐项检查所有打分项时，人工审阅不能提交。

### 6.7 发布和回滚

用户可以将候选运行配置发布为已发布配置。

发布前必须展示：

- 改动清单。
- 生效范围。
- 评测覆盖情况。
- 程序断言结果。
- 人工审阅结果。
- 风险提示。

正常发布条件：

- 至少有一个评测运行。
- 至少有一个评测运行通过程序断言。
- 人工审阅评分只作为参考依据，不阻塞发布流程。

强制发布要求：

- 明确选择强制发布原因。
- 填写本机审计备注。
- 发布记录标记为强制发布。

回滚要求：

- 可以回滚到历史已发布运行配置。
- 回滚必须生成发布记录。
- 回滚后普通运行使用回滚目标配置。

验收标准：

- 用户能清楚知道发布会影响哪些范围。
- 未通过 gate 的候选不能普通发布。
- 强制发布和回滚都有审计记录。

### 6.8 关键交互细节

本节补齐需要在 UI 实现中明确落地的交互规则。所有规则都遵循同一个原则：用户可以先进入配置表单并试改，但只有点击保存或下一步且校验通过后，才创建新版本、候选、审阅或发布记录。

#### 新建配置流程

新建配置流程从入口列表触发，进入独立的配置流程页，不在列表页弹窗展开。

交互顺序：

1. 用户点击“新建配置流程”。
2. 系统要求选择产品、目标 agent 或全产品范围，并预填当前 active 运行配置作为基线。
3. 系统生成一个未保存的流程草稿表单，自动命名为“产品 / 目标范围 / 时间”，用户可以改名。
4. 用户必须至少在一个节点完成真实修改，例如 Agent 配置、评测案例绑定、评测运行配置、断言配置或审阅模板绑定。
5. 用户点击保存草稿或下一步时，系统校验名称、产品、目标范围和节点输入是否合法。
6. 校验通过后才创建流程记录；如果没有任何真实修改，只允许保存为空草稿说明，不生成候选运行配置。

防错规则：

- 选择“新建...”不显示成功 toast，只显示未保存状态。
- 离开页面前如存在未保存修改，需要提示保留草稿、放弃修改或继续编辑。
- 已经绑定 EvalRun 的候选再次修改 Agent 配置后，相关 EvalRun 标记为“基于旧候选”，发布 Gate 不再把它当作有效通过证据。
- 流程名、节点配置名和版本时间必须在人类可读列表中可区分。

#### Agent 配置编辑与 diff

Agent 配置编辑区必须支持三类内容的并行修改：Agent 提示词、工具说明和行为规则。

提示词编辑交互：

- 左侧按 agent 列表选择，例如 system-agent、story-agent、reviewer-agent。
- 中间显示当前编辑器，包含名称、生效范围、来源版本、提示词正文和备注。
- 右侧或下方显示结构化 diff，但该 diff 必须有足够宽度，不应压缩成长行难读的小栏。
- diff 需要同时支持“整段对比”和“变更摘要”。整段对比用于精读，摘要用于列表和发布 Gate。
- 保存前校验 agentId、范围、正文非空、版本差异和引用合法，不校验提示词语义内容。

工具说明编辑交互：

- 工具列表按 toolId 分组，选择工具后展示正式工具主描述、参数说明和输出说明。
- 用户可以分别编辑主描述、单个参数说明和输出说明。
- 每个字段展示 active 值、候选值和变更状态，例如未改、已改、待补全。
- 多个工具说明可以在同一个 Agent 配置节点内一起修改，保存时合并为一个候选运行配置，但改动清单必须按 toolId 拆开。
- Harness 只校验 toolId 存在、字段结构完整、参数引用合法和存在真实差异，不校验内容语义风险。

行为规则编辑交互：

- 行为规则以列表或表格展示，字段包括标题、范围、启停状态、来源版本和引用位置。
- 用户可以新增规则、编辑规则、停用规则或从历史规则派生。
- 停用不是删除；被评测或发布引用过的规则只能归档或在新候选中取消引用。
- 多条行为规则修改时，改动清单必须逐条列出规则标题、范围、启停变化和正文 diff。

diff 展示规则：

- 发布 diff：比较 candidate 运行配置和当前 active 运行配置，回答“发布后普通 run 实际会变什么”。
- 片段 diff：比较某个提示词、规则或工具说明的新旧版本，回答“这段配置文本改了什么”。
- 断言配置 diff 和审阅模板 diff 不进入普通运行发布 diff，但应在评测节点和发布证据中展示，因为它们解释本次评测是如何判断的。

#### 断言配置交互

断言配置在步骤三中是主编辑对象。评测运行配置作为紧凑执行参数区，断言配置占据主要编辑面积。

断言新增交互：

1. 用户在断言配置选择框中选择历史配置或“新建断言配置...”。
2. 新建时系统打开未保存表单，预填名称、分组和空断言列表。
3. 用户点击“新增断言”，先选择断言类型，再填写该类型需要的字段。
4. 断言类型至少包含文件变化、路径约束、Markdown section、工具事件、diff 限制和现有结构合规。
5. 每条断言都有启用状态、失败等级、目标对象、比较条件和说明。
6. 用户可以复制、停用、删除未引用断言；已被运行结果引用的断言版本只能派生新版本后修改。
7. 保存或下一步时逐条校验结构合法性，并在顶部汇总错误数量和定位入口。

断言表单展示规则：

- 左侧或顶部为分组导航，显示每组启用数量、禁用数量和错误数量。
- 主区域展示断言列表和当前断言编辑表单。
- 当前断言表单按类型动态展示字段，例如文件路径、工具 ID、参数路径、比较操作符、数量限制、section 名称。
- 断言结果回读时，需要能从失败结果跳回对应断言配置项。
- Harness 只做结构、引用、启停和可执行性校验，不判断断言是否合理或是否覆盖业务风险。

#### 人工打分交互

人工打分与评测报告是步骤四的两个平级主工作区。人工打分不是评测报告的右侧侧栏。

逐项打分规则：

- 系统按审阅模板渲染所有打分项。
- 每个打分项必须在“已评分”和“不涉及”之间做出显式选择。
- 已评分项必须填写 1-10 分，支持整数分；后续可扩展半分，但第一版不要求。
- 不涉及项不填写分值，不参与总分，但可以填写原因备注。
- 总分按涉及项权重重新归一化计算，避免不涉及项把总分拉低。
- 未逐项检查完成时，提交按钮禁用，并展示未完成项定位。

新增打分项交互：

1. 用户点击“新增打分项”。
2. 系统在当前打分表末尾插入未保存行，字段包括名称、说明、权重、是否必评、备注提示。
3. 新增项默认不直接写回原模板；用户需要选择“仅用于本次审阅”或“派生模板后复用”。
4. 如果选择派生模板，系统生成模板派生表单，保存后当前审阅改用新模板版本。
5. 新增项必须名称非空、权重合法，才能参与提交。

调整权重交互：

- 用户可以在打分表中直接编辑权重，或打开“调整权重”面板批量修改。
- 面板需要显示当前总权重、涉及项权重、未涉及项处理方式和保存后影响。
- 权重校验可以允许总和为 100，也可以允许任意正数后按比例归一化，但规则必须在界面中固定展示。
- 保存权重修改不会静默改变原模板；如果该模板已被历史审阅引用，必须派生新模板版本。

派生模板交互：

1. 用户从审阅模板选择框选择历史模板，或在当前模板上点击“派生模板”。
2. 系统复制模板内容并生成未保存表单，自动命名为“原模板名 / 派生 / 时间”。
3. 用户可以新增、删除、重命名打分项，调整权重和备注提示。
4. 保存前校验至少一个打分项、权重合法、决策选项完整。
5. 保存后生成新模板版本，并把当前审阅表单切换到该模板；原模板不受影响。

#### 发布、强制发布与回滚交互

发布页只做决策和审计，不再编辑配置内容。

普通发布交互：

1. 用户进入发布检查。
2. 系统展示 candidate 与 active 的发布 diff、影响范围、评测覆盖、程序断言、人工审阅和未解决风险。
3. Gate 全部通过时，“普通发布”启用。
4. 用户确认发布摘要并填写可选备注。
5. 系统将 candidate 设为 active，旧 active 归档，并生成发布记录。

强制发布交互：

- Gate 未通过时普通发布禁用，但用户可以选择强制发布。
- 强制发布必须选择原因，例如紧急修复、评测样本不足但人工确认、断言误报、临时回避问题。
- 强制发布必须填写本机审计备注，备注为空不能提交。
- 发布记录必须保存 force 标记、原因、当时 Gate 失败项、发布 diff 和人工备注。

回滚交互：

1. 用户从历史已发布版本或发布记录中点击“回滚到此版本”。
2. 系统展示当前 active 与回滚目标的 diff、回滚后影响范围和会被替换的配置片段。
3. 用户填写回滚原因；原因为空不能提交。
4. 系统创建一条新的 active 版本或切换 active 指针，并写入回滚发布记录。
5. 回滚后普通 run 读取回滚目标配置；被回滚掉的版本归档但保留评测和发布证据。

删除和归档交互：

- 未被引用的草稿可以硬删除。
- 被 EvalRun、HumanReview、断言结果或发布记录引用过的对象不能硬删除，只能归档。
- 删除或归档前必须展示引用数量和受影响列表。

## 7. 推荐用户流程

### 7.1 修改工具说明

1. 用户从入口列表新建或打开一个本地配置流程。
2. 进入 Agent 配置节点。
3. 在同一个选择框中选择历史 Agent 配置，或选择“新建 Agent 配置...”打开未保存表单。
4. 选择工具，查看当前正式工具说明、参数说明和输出说明。
5. 修改说明，并填写或确认配置名称。
6. 用户点击保存或下一步，系统校验存在真实差异、内容合法和生效范围明确。
7. 校验通过后生成候选运行配置。
8. 用户选择或复用评测案例上下文、评测运行配置、断言配置和审阅模板执行评测。
9. 用户人工审阅并自行决定发布。

### 7.2 修改某个 agent 的提示词

1. 用户从入口列表新建或打开一个本地配置流程。
2. 进入 Agent 配置节点。
3. 在同一个选择框中选择历史 Agent 配置，或选择“新建 Agent 配置...”打开未保存表单。
4. 选择 agent，查看当前提示词。
5. 修改提示词，并填写或确认配置名称。
6. 用户点击保存或下一步，系统校验存在真实差异、内容合法和生效范围明确。
7. 校验通过后生成候选运行配置，改动范围标记为该 agent。
8. 用户运行该 agent 相关评测案例上下文，并选择断言配置和审阅模板。
9. 用户审阅并发布。

### 7.3 新增行为规则

1. 用户从入口列表新建或打开一个本地配置流程。
2. 进入 Agent 配置节点。
3. 在行为规则区域选择历史规则或选择“新建行为规则...”打开未保存表单。
4. 新增规则标题、正文和生效范围。
5. 用户点击保存或下一步，系统校验规则标题、正文、生效范围和引用关系是否合法。
6. 校验通过后生成候选运行配置。
7. 用户选择覆盖该规则影响范围的评测案例上下文、断言配置和审阅模板。
8. 用户审阅并发布。

### 7.4 从失败运行创建评测案例上下文

1. 用户选择失败运行记录。
2. 系统用运行证据定位对话起点，并提取对话开始前的上下文、工作区快照、固定记忆和固定知识库输入。
3. 文件变化和工具调用只作为背景证据展示，不写入案例断言。
4. 用户确认或裁剪上下文。
5. 用户点击保存或下一步，系统校验上下文完整性和引用关系合法性。
6. 校验通过后保存案例上下文到案例库。
7. 后续候选运行配置可以复用该案例上下文评测。

### 7.5 新建并复用断言配置

1. 用户进入评测运行配置节点。
2. 在断言配置选择框中选择历史断言配置，或选择“新建断言配置...”打开未保存表单。
3. 用户添加文件变化、路径、工具调用或 diff 限制等断言。
4. 用户点击保存或下一步，系统校验至少一条断言有效且可执行。
5. 校验通过后保存断言配置，并绑定到本次评测运行配置。

### 7.6 新建并复用人工审阅模板

1. 用户在评测运行配置节点或人工审阅开始前选择审阅模板。
2. 在同一个选择框中选择历史模板，或选择“新建审阅模板...”打开未保存表单。
3. 用户配置打分项、权重、决策选项和备注提示。
4. 用户点击保存或下一步，系统校验至少一个打分项、权重合法、决策选项完整。
5. 校验通过后保存模板，并用于渲染人工审阅表单。

### 7.7 发布候选运行配置

1. 用户选择候选运行配置。
2. 系统展示相对当前已发布版本的改动清单。
3. 系统展示评测和人工审阅结果。
4. 系统展示发布 gate。
5. 用户确认发布。
6. 系统生成发布记录，并将候选设为已发布配置。

## 8. 评测覆盖规则

不同生效范围的改动需要不同评测覆盖。

| 改动范围 | 推荐最低评测覆盖 |
| --- | --- |
| system | 至少覆盖每个受影响产品的一组 smoke 评测。 |
| product | 至少覆盖该产品核心 agent 流程。 |
| agent | 至少覆盖该 agent 相关案例。 |

不同改动类型也需要不同关注点。

| 改动类型 | 重点检查 |
| --- | --- |
| Agent 提示词 | 输出质量、职责边界、是否误用工具。 |
| 行为规则 | 是否改善目标问题，是否误伤其它流程。 |
| 工具说明 | 工具调用时机、参数正确性、敏感操作边界。 |
| 普通运行策略 | 模型质量、成本、记忆写入和检索行为。 |
| 评测运行配置 | Repro/Live 选择、模型临时覆盖、memory/knowledge 固定输入和工具 mock 是否符合验证目标。 |
| 断言配置 | 断言是否可执行、是否覆盖目标风险、是否过宽或过窄。 |
| 人工审阅模板 | 打分项是否覆盖人工质量判断、权重是否合理、决策选项是否完整。 |

## 9. 本机风险控制

1. 草稿和候选配置不影响普通运行。
2. 只有已发布运行配置影响普通运行。
3. 删除应受到引用保护，已有评测或发布记录引用的对象不得硬删除。
4. 强制发布必须写本机审计原因。
5. system 范围改动需要更强提示，因为可能影响本机多个产品。
6. 工具说明只做结构合法性校验，例如 toolId、主描述、参数说明和输出说明是否完整。
7. 新建节点配置只打开表单，不得直接保存并提示成功；必须完成修改并通过校验后才保存。
8. 本系统不设计管理员权限、多人审批或发布审核人。

## 10. 成功指标

1. 用户能在 1 分钟内判断当前产品普通运行使用哪套配置。
2. 用户能清楚判断一次候选改动影响 system、product 还是 agent。
3. 发布前所有候选都有可追溯的评测和人工审阅记录。
4. 从失败运行沉淀评测案例上下文的流程可完成，不需要手动复制大量上下文。
5. 发布记录能解释每次配置变化、评测依据和发布原因。
6. 用户可以在各节点复用历史配置，也可以新建表单并在校验后保存。
7. 用户不会把评测案例、断言配置和人工审阅模板混为一个概念。

## 11. 待确认问题

1. agent 级工具说明覆盖是否第一版开放，还是只开放 product 级工具说明。
2. 行为规则是否允许跨产品共享，还是先以 product 范围为主。
3. 评测覆盖 gate 是否按影响范围自动推荐必跑案例上下文和断言配置。
4. 发布后是否需要自动提示受影响产品或 agent 的 smoke 评测状态。
5. 手动创建评测案例上下文第一版是否开放，还是仅保留入口和后续预留。
